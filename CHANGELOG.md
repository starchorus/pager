## 0.2.6.2 - 2026-10-30

*A part release of the 0.2 line: it carries the review fixes once marked for 0.2.6.1, never released on their own, together with the adaptation to Pager firmware 2.0.*

### Added

- **The firmware's own Bluetooth database as a passive source on firmware 2.0 (`blue5.db`).** On 2.0 the Pager's resident Bluetooth scanner holds the controller, so the collector's own passive LE window stands down (`bt_begin` returns without starting a tool) and, with `STARCHORUS_BLUETOOTH=1`, the Bluetooth layer reads that scanner's database instead. The new `STARCHORUS_BT_SOURCE` (`auto`, the default, `blue5` or `window`) chooses the source and `STARCHORUS_BLUE5_DB` (default `/root/recon/blue5.db`) its path; `auto` takes the database when it exists, otherwise the window. The file is copied to RAM and read with `sqlite3 -readonly`, as the recon database is, but with no flash copy and no reading of the live file: no copy means no Bluetooth that cycle. It is read-only throughout: Starchorus never starts, stops or configures the scanner and never runs `blue5ctl` (both are denied by name in the passivity check). Whatever mode the scanner runs in is the Pager's own setting, outside Starchorus's control; reading the result sends nothing. The document carries `center.bt_source` and `bt_hold`, and no `bt_window`. Set out in `SECURITY.md`, `docs/device-notes.md` §2c, `docs/architecture.md` and the collector's header, with new `blue5:` self-test cases.
- **Access-point security from the 2.0 beacon JSON.** On 2.0 the AP service's beacon records carry the libwifi `encryption` bitmask. The opt-in `pineap` source now decodes it for each access point's security (the same labels, `akm`, `cipher` and `auth` the recon-database path gives) instead of looking the security up in the database, whenever a beacon carries it; an access point a beacon has not named falls back to the database lookup as before, so the lookup is skipped for the access points the JSON already covers. The bitmask is the full libwifi value (the class bits low, the cipher and AKM fields high); it is read from its decimal string so that BusyBox `awk` never rounds it away at 2^53. Set out in `docs/device-notes.md` §5a (with the open device questions) and the `pineap` paragraphs of `README.md` and `SECURITY.md`, with new `pineap 2.0:` self-test cases.
- The collector's `--help` names the opt-in layers and their defaults.
- The version grammar admits a fourth number, so `0.2.6.2` and its kin are read where only three were before.
- **Bluetooth company names for the firmware's database (firmware 2.0).** `blue5.db` holds each company as its Bluetooth SIG identifier alone, where the collector's own window had btmon's decoded name, so the page and the Overview showed `company id 76` for what the window had named `Apple, Inc.`. The collector now names the identifier from the firmware's own list, `/lib/hak5/bt_companies.txt` (one `id<TAB>name` line per identifier, the id four hex digits; 4,041 lines on the device), read once at start and again with the hourly vendor re-check, like the OUI file: a text file that is read, nothing started. `STARCHORUS_BT_COMPANIES_FILE` (`auto` | path) chooses the list; without a usable one the identifier stands alone, as before, with one log line. The page and the Overview are unchanged: they show the name whenever the capture carries one. A new `blue5:` self-test case names 76 from a list of its own and leaves an identifier the list lacks bare.
- `.github/FUNDING.yml`: the repository's Sponsor button points at GitHub Sponsors (the handle `starchorus`).

### Changed

- **The `pineap` recent list uses the 2.0 argument `bytime=true`.** Firmware 2.0 rejects the former `sort=time sortdir=desc` of the one bounded `RECON DEVICES` call with exit 255; the newest-first ordering is asked as `bytime=true limit=400` now, checked read-only on the device (the transmit counters unchanged). It bears only on `STARCHORUS_SOURCE=pineap` in its default `recent` mode; the default source (the recon database) is untouched. The pinned `apcli_ro` contract line and its provenance move with it.
- **The collector's start and main loop.** The old loop is replaced before an interface or `airodump` is chosen; a monitor interface is claimed only when it is really there, only the monitor interface this run made is brought up, and the monitor VIF and the active scan are kept off the management radio. The traps are set before anything is made, and every temporary name is cleaned up. Unknown options are refused, the recon window is normalised, and the cycle burst is kept off the sleep pace. The ACTIVE-scan notice and a `pineap` lookup failure reach the log now.
- `tools/cdp.py`: a stale report is cleared when `runq` fails before `cdp.py` runs.
- The fuzz sensor's own proof (`fuzz_verdict`, probe mode) counts an anchor that finds a sink showing the hostile text unmasked as the planted escaping fault seen through another sink, not as an unplanned finding: with `esc` reduced to `String(s)` every masking anchor must fail. The two BLIND checks and the run mode (the real page masks, and its anchors count) are unchanged.
- Two page-pixel rows measure what they claim again after the first-time placements of #41 moved the planted stars. The WarGames phosphor probe samples the afterglow at 2.3 times the star radius: at 1.9 the samples sat about 1.25 px outside the WPA3 ring's edge, where a sample rounded to a whole pixel read ring bleed that swamped the freshness tiers once the stars stood at other sub-pixel positions. The constellation-label fixture uses addresses whose hashed places keep the group label's one candidate off the grid cell the empty core text owns; with the former addresses `place()` dropped the label, as documented. The pins of both rows are unchanged.
- **The passivity mutation probe runs as shards and replays a green result when nothing changed.** It was two processes, the default run and `--meta`, and the longer of the two (the `--meta` half, not the main one) took 73 minutes on the development machine under load. Its entries are independent, so `tools/passivity-mutate.sh` gains `--shard I/N` (the entries whose turn it is, their lines tagged, then the sums) and `--merge` (one verdict from the summed counters, in the order of the table, per mode; it refuses a shard that is missing, cut short, doubled or of the other mode, and is never green with fewer entries); `tools/regress.d/mutation-probe.sh` starts the shards of both modes at the same time, ten in all by default (`STARCHORUS_MUTATE_JOBS`, 1 to 64), and `self_guard` still counts 2/1/1/0, since the script starts nothing new. The merged reports are byte for byte those of the two halves (full runs with five and five, and six and six shards, 30 October 2026), the morning's planted blind spot (`MIN_SQLITE_CALLS` back at one) is reported as before, and the run takes about sixteen minutes on a 14-core machine. The drop-in also keeps the reports of a green run under `out/mutation-memo`, keyed by the SHA-256 of every input (the probe, the checker, the page, the shell scope as the checker lists it, the device probe, the denylist checker and its lists, the programs that run them and the system), and replays them under a note when nothing changed, in about a second; any doubt, a red result or `STARCHORUS_MUTATE_FRESH=1` runs the probe in full. The pre-commit hook runs in a fresh export, so it runs the probe in full unless `STARCHORUS_MUTATE_MEMO_DIR` points it at a lasting directory.
- **Seven more page-pixel rows measure what they claim after the first-time placements of #41**, re-measured on the pinned Chrome 153.0.8010.48 and on 156 alike (the browser was not the cause), none a defect of the page. The vendor-off reference figures of the labels rows (`LBL_VEN_OFF`, a comparison with the page before the vendor change, not a claim) are the measurements of the 0.2.6.2 page, and the text-budget row's counts of the radio-pair fixture's labels record one 3D label fewer while its claim, the same labels with the Bluetooth layer on, off and on, holds as before. The group-label and badge comparison with the vendor switch on and off is read at 1728 x 1117: at 1440 x 900 an AP's two-row vendor rectangle took the grid cell of a group label's one candidate, which the grid, first come, gives to no priority, as `docs/architecture.md` says of the second row; the row's title says so now. The locked-label sensor bites when a copy that places the client vendor lines ahead of every AP label drops a locked label anywhere, the pair of the row above or one of the thirteen sweeps, the complement of that row's pass (the one pair alone could bite only by placement luck, and cannot since #41). The phone row's margin-less copy looks from the desktop camera at el 1.1, where its stars reach the rim again in both layouts (the real page has no label box outside in any of the eight states). The Whitehall new-plot probe samples at px+10, clear of the old access point's own outer ring, which it read at px+9 once that star stood at another sub-pixel position. Every pin of a claim is unchanged.

### Fixed

- The installer ends a dead SSH link after about a minute (the `ServerAlive` options).
- The known-open fuzz entry for the generated bound is retired.
- Rows for 'Back to live': no false 'security changed', no false cue.
- **The payload's Start on firmware 2.0 ended in 'Could not start. See the log.' while the collector was sound.** The menu's `pl_wait_up` allowed the launched collector five seconds to register its loop pidfile and five more while it lived, then gave up and killed it; on the Pager the pidfile can land well after that while nothing is wrong (the collector's own start waits for an earlier loop, `replace_loops`, up to `STARCHORUS_INTERVAL + 15` s, and it runs at nice 19 beside the spinner and the page server). The wait now lasts for as long as the launched collector is alive without a pidfile, up to the collector's own ceiling plus five seconds, and still gives up at once when that process has gone, so a collector that cannot start is reported as before. The Settings restart shares the wait. Verified against the payload's own interface rows (`tools/regress.d/payload-ui.sh`, the failed-Start row among them) and, on 30 October 2026, by a Start from the Pager's own menu with the new payload.
- **The collector's self-test read the device's real Bluetooth database on firmware 2.0.** Its Bluetooth cases were not pinned to the synthetic window source: with `STARCHORUS_BT_SOURCE=auto` and `/root/recon/blue5.db` present, `bt_pick` chose the database, six cases failed with real figures and one case's message printed real addresses. The self-test now pins the source to the window and the database and company-list paths to names that do not exist, as it already pins the alert directory; a case that reads a database or a list sets its own. On a development machine `STARCHORUS_BLUE5_DB=<any existing file> sh starchorus-collect.sh --selftest` reproduces the device's six failures without this change and passes with it; on the Pager, the installer's own run of the self-test ends VERIFIED for the first time on firmware 2.0 (531 checks on the device as of 30 October 2026; the development machine runs 543, the difference being cases gated on tools the device lacks).
